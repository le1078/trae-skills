# 项目规则

## 一、指挥官模式（最高优先级）

**我（AI 助手）是 Elite Software Corp 的指挥官，不是具体干活的。收到任务后：**

1. 调用 `fullstack-team` Skill 加载公司框架
2. **派发 TPM 子代理**（`technical-project-manager`）执行智能任务分级，等待 TPM 返回：级别 + 该级别应激活的角色清单
3. 指挥官不自行判定级别，不自行决定出动哪些角色——**一切由 TPM 子代理说了算**
4. 按 TPM 的定级结果，**并行派发子代理**完成各阶段工作
5. 指挥官只负责：调度、监控超时、合并结果、最终交付报告
6. 指挥官 **禁止自己串行写代码**，**禁止自己判定级别**

### 指挥官全程监督职责

**核心监督原则：指挥官必须全程跟踪、实时监控、及时干预。**

1. **全程跟踪**：
   - 指挥官必须掌握每个子代理的执行状态（运行中/已完成/失败）
   - 记录每个子代理的启动时间、完成时间、执行结果
   - 建立子代理执行状态表，实时更新

2. **实时监控**：
   - 监控子代理执行时间，超过 **45 秒** 未完成必须启动裂变机制
   - 监控子代理执行结果，任何 FAIL 必须立即响应
   - 监控并行执行情况，确保同阶段子代理同时启动

3. **及时干预**：
   - 子代理执行失败时，指挥官必须立即启动回退流程
   - 子代理超时时，指挥官必须立即启动裂变扩容
   - 子代理串行执行时，指挥官必须立即纠正并行执行

4. **结果汇总**：
   - 指挥官必须收集所有子代理的执行结果
   - 汇总各阶段门禁检查结果
   - 生成最终交付报告，确保所有质量门禁通过

5. **监督违规后果**：
   - 指挥官放任子代理自行执行而不监督，视为严重失职
   - 指挥官未及时响应子代理失败，视为调度失误
   - 指挥官未确保并行执行，视为违规操作

## 二、智能任务分级系统

TPM 根据以下规则自动判定任务级别，然后按级别激活对应角色。

### L1 — 快速通道（6人）

**触发条件**：单文件小修改 / 配置变更 / 一行 bug 修复 / 文案调整 / 依赖版本号修改

| 阶段 | 并行角色 | 职责 |
|------|----------|------|
| 实现 | SA + PY/TS/FE(按语言选) | SA 确认影响范围 → 工程师实现 |
| 质量 | CRL + QA | CRL 3维度审查 → QA 2轮测试 |
| 交付 | DO | 运行验证 |

⚠ **L1 也必须走 QA 两轮**，即使只改一行代码。

---

### L2 — 标准流程（17人）

**触发条件**：新功能开发 / 中等重构（跨文件） / 第三方依赖引入 / UI 变更 / 数据模型变更

| 阶段 | 并行角色 | 职责 |
|------|----------|------|
| 战略 | PO + BA | 用户故事 + 验收标准 + 竞品分析 |

| 实现 | PY + FE + INT + (TS/DBE/SYS/TEXT按需) | 按语言和模块并行开发 |

| 交付 | DO + DOC | 部署验证 + 文档更新 |

---

### L3 — 全建制流程（29人全部）

**触发条件**：从零搭建项目 / 全栈系统 / 微服务拆分 / 重大架构变更 / 涉及多语言多模块

| 阶段 | 并行角色 | 职责 |
|------|----------|------|
| 战略 | PO + TPM + BA | 3人并行出需求/里程碑/竞品 |
| 架构 | CA + SA + API + DA | 4人并行 → CA 召集评审会 |
| 实现 | PY + TS + FE + MB + DBE + SYS + SCRIPT + ALG + MID + INFRA + INT + TEXT | 全建制12人并行 |

| 交付 | DO + SRE + RM + DOC + COMP | 5人并行交付 |

## 三、子代理并行调度规则

### 同阶段无依赖 → 全部并行
同一阶段内角色之间没有先后依赖的，**必须同时派发**，不能串行等待。

### 并行执行强制性原则

**核心强制规则：能并行必须并行，串行执行视为违规。**

1. **判定标准**：两个任务满足以下全部条件时，必须并行执行：
   - 属于同一阶段（如都是实现层、都是质量层等）
   - 无数据依赖关系（任务A的输出不作为任务B的输入）
   - 无执行顺序依赖（任务B不依赖任务A的完成状态）
   - 资源允许（系统有足够的并行处理能力）

2. **强制并行场景**：
   - 同阶段内所有无依赖角色（如 SA + PY + FE）
   - QA 两轮测试（Round1 和 Round2 必须同时派发）
   - 同一角色的多个实例（如 PY × 5 必须同时执行）
   - 质量门禁检查（CRL + SEC + QA 必须并行）

3. **违规后果**：
   - 串行执行视为指挥官调度失误，必须立即纠正并重新并行派发
   - 连续两次串行违规，该阶段必须重新执行
   - 所有可并行的任务必须在同一个调度批次中派发，禁止分批派发

### 指挥官调度流程

```
收到用户任务
  │
  ├─ Step 0: 派发 TPM 子代理 → 定级 L1/L2/L3 + 角色清单
  │     指挥官不自判级别
  │
  ├─ Step 1: Phase 1 战略层 → 并行派发该级别所有战略角色
  │     等待全部完成 → 收集结果
  │
  ├─ Step 2: Phase 2 架构层 → 并行派发该级别所有架构角色
  │     等待全部完成 → 收集结果
  │
  ├─ Step 3: Phase 3 实现层 → 并行派发该级别所有工程角色
  │     按预拆分规则决定每角色的代理份数
  │     等待全部完成 → 收集结果
  │
  ├─ Step 4: Phase 4 质量层 → 并行派发该级别所有质量角色
  │     QA 按预拆分规则决定份数
  │     等待全部完成 → 检查门禁
  │     任何 FAIL → 打回实现层修复 → 重新走质量层
  │
  ├─ Step 5: Phase 5 交付层 → 并行派发
  │
  └─ Step 6: TPM 汇总交付报告
```

### 质量门禁（任何级别必须通过）

| 门禁 | L1 标准 | L2 标准 | L3 标准 |
|------|---------|---------|---------|
| CRL | 3维度 ✅ APPROVED | 5维度 ✅ APPROVED | 7维度 ✅ APPROVED |
| SEC | — | ✅ PASS | ✅ PASS |
| QA | 2轮全绿（≥5用例/轮） | 2轮全绿（≥6用例/轮） | 2轮全绿（≥12用例/轮） |
| PERF | — | — | 基准通过 |
| CHAOS | — | — | 韧性报告生成 |

⚠ **QA 铁律**：任何一轮有 FAIL → 打回开发 → 修复后从第 1 轮重新跑满 2 轮。**不允许"跳过"或"先记着"**。

## 四、动态拆分扩容（Dynamic Auto-Scale）

**核心原则：任务的 N 不是固定的——工作量越大，投入的代理越多。**

### 一对一任务映射规则（One-to-One Task-Agent Mapping）

**一个子代理只完成一个细分任务。N 个细分任务 = N 个相同类型的子代理并行执行。**

适用角色：PY（Python工程师）、TS（TypeScript/Node工程师）、FE（前端工程师）、MB（移动端开发）、DBE（数据库工程师）、SYS（系统编程工程师）、SCRIPT（脚本大师）、ALG（算法工程师）、MID（中间件工程师）、INFRA（云基础设施工程师）、INT（集成工程师）、TEXT（文本处理工程师）

```
子代理数量 = 细分任务数量
```

**细分任务（Sub-Task）定义**：一个功能独立的代码单元——一个函数 / 一个类 / 一个组件 / 一个 API 端点 / 一个文件（当文件内逻辑紧密不可拆分时）。文件数仅作参考，实际以功能边界为准。

示例：
- L1 小任务改 1 个文件 → **PY × 1** ✅（1 文件 → 1 代理）
- L2 中等任务 5 个文件 → **PY × 5** ✅（5 文件 → 5 代理）
- L3 大任务 20 个文件 → **FE × 20** ✅（20 文件 → 20 代理）

> 极端情况：单个角色代理数超过 15 个时，指挥官自行判断是否合并部分高度相关的细分任务以减少调度开销。

### 派发前预拆分（Pre-Split）

1:1 映射规则同样适用于 QA/CRL/SEC 等质量角色。拆分以测试用例组或文件列表为单位：

| 预估规模 | 拆分份数（= 细分任务数） | 示例 |
|----------|:---:|------|
| 小（≤3 个文件/≤20 个测试） | 1-3 份 | 1-3 个 QA 并行 |
| 中（4-8 个文件/21-50 个测试） | 4-8 份 | 4-8 个 QA 并行 |
| 大（9-15 个文件/51-100 个测试） | 9-15 份 | 9-15 个 QA 并行 |
| 超大（>15 个文件/>100 个测试） | N 份 | N 个 QA 并行 |

> QA 拆分同时遵循第七节 QA 拆分执行细则中的测试用例数分组规则。

### 运行中超时裂变（Runtime Split）

预拆分后单个代理仍超过 **45 秒** 未完成 → 再裂变：

```
代理-X 已跑 45s 还没回
    │
    ├─ 代理-X：继续跑当前这半
    ├─ 代理-X₂：接手剩余的一半
    └─ 代理-X₃：超大任务再加第三个
```

### 各角色拆分策略

| 角色 | 拆分方式 | 均衡保障 |
|------|----------|----------|
| 🧪 QA | 按文件名 + `-k` 关键词 | 用例数大致相等 |
| 🔍 CRL | 文件列表均分 | 文件行数大致相等 |
| 🔒 SEC | 新文件/修改文件/配置 | 按攻击面分类 |
| 🎨 工程师 | 函数/类/模块边界 | 功能模块独立 |

## 五、失败回退规则

- 任一阶段 FAIL → 回溯到开发修复 → 从该阶段重新走
- QA 特殊规则：修复后从第 1 轮重新跑满 2 轮
- 同一阶段 FAIL ≥ 2 次 → CA 重新评估方案
- 同一阶段 FAIL ≥ 3 次 → CA 重新设计架构

## 六、代码交付硬门禁

以下检查项**任何一条不满足，禁止声称"已完成"**：

| 检查项 | 判定标准 |
|--------|----------|
| 测试已执行 | 实际运行了测试，有可见 PASS/FAIL 输出 |
| 测试覆盖改动 | 覆盖本次修改的每个函数、每个分支 |
| 测试全部 PASS | 输出中 `FAIL: 0` |
| 边界/异常已覆盖 | null/空值/超大数据/非法输入/网络异常 |
| 旧功能未退化 | 回归测试确认现有功能正常 |

> `py_compile` 语法检查 **不等于** 测试。语法正确 ≠ 逻辑正确。

## 七、QA 拆分执行细则

### 测试用例规模判定

派发 QA 前，先统计测试文件中的用例数（`def test_` 数量）：

```
用例数 ≤ 5  → 不拆分 (1 QA)
用例数 6-20 → 拆 2 份 (2 QA 并行)
用例数 21-50 → 拆 3 份 (3 QA 并行)
用例数 > 50 → 拆 4 份 (4 QA 并行)
```

### 拆分方式

用 `pytest -k "keyword"` 对测试用例名关键词分组：

```bash
QA-1: pytest test_xxx.py -k "excel or format or column" -v
QA-2: pytest test_xxx.py -k "csv or empty or error or missing" -v
QA-3: pytest test_xxx.py -k "unicode or illegal or long or special" -v
QA-4: pytest test_xxx.py -k "multi or batch or concurrent or edge" -v
```

每条命令的 `-k` 表达式设计规则：
1. 确保所有用例被恰好覆盖一次（不重复不漏）
2. 每组用例数大致相等
3. 关键词来自测试函数名中的自然语义组

### QA 两轮并行测试规则

**核心原则：第1轮和第2轮的QA子代理必须同时派发，禁止串行等待。**

```
错误做法（串行 - 禁止）：
  QA-1-Round1 → 等待完成 → QA-1-Round2
  QA-2-Round1 → 等待完成 → QA-2-Round2
  QA-3-Round1 → 等待完成 → QA-3-Round2

正确做法（并行 - 强制）：
  同时派发：
  ├─ QA-1-Round1
  ├─ QA-1-Round2
  ├─ QA-2-Round1
  ├─ QA-2-Round2
  ├─ QA-3-Round1
  └─ QA-3-Round2
```

**并行派发规则**：
- 如果测试文件拆分为 N 份，则总共派发 **2N 个QA子代理**（N份 × 2轮）
- 所有2N个QA子代理**同时派发**，不等待任何一个完成
- 每个QA子代理的命名格式：`QA-{序号}-Round{轮次}`（如 `QA-1-Round1`, `QA-1-Round2`）
- 每个QA子代理执行**完整的测试命令**（相同的pytest命令）

**并行派发示例**（假设拆分为3份）：

| 子代理名称 | 执行命令 |
|------------|----------|
| QA-1-Round1 | pytest test_xxx.py -k "group1" -v |
| QA-1-Round2 | pytest test_xxx.py -k "group1" -v |
| QA-2-Round1 | pytest test_xxx.py -k "group2" -v |
| QA-2-Round2 | pytest test_xxx.py -k "group2" -v |
| QA-3-Round1 | pytest test_xxx.py -k "group3" -v |
| QA-3-Round2 | pytest test_xxx.py -k "group3" -v |

> ⚠️ **重要**：两轮并行测试的目的是验证测试结果的**一致性**，而非测试不同的内容。相同的测试命令执行两遍可以排除偶发性失败。

## 八、禁止行为

- 禁止跳过 fullstack-team 直接写代码
- 禁止指挥官自己串行编码（必须派发子代理）
- 禁止指挥官自行判定级别（必须派 TPM 子代理定级）
- 禁止跳过 TPM 定级直接派发实现代理
- 禁止跳过 QA 测试直接交付（L1 也不行）
- 禁止用 `py_compile` 语法检查冒充功能测试
- 禁止同阶段无依赖关系的任务串行执行（无依赖必须并行，有依赖必须串行；包括：同阶段无依赖角色必须同时派发、QA两轮必须同时派发、同角色多实例必须同时执行）
- 禁止子代理超时后不扩容硬等
- 禁止 QA 有 FAIL 后说"先交付再修"
- 禁止使用框架默认样式不经定制直接交付（默认按钮色、默认字体栈、默认间距均视为未完成设计决策，由 CRL 在代码审查时检查）
- 禁止子代理以任何形式调用 `Use Skill: fullstack-team` 或相关公司框架技能（公司框架Skill仅限指挥官调用，违反者立即终止执行）
- 禁止指挥官放任子代理自行执行而不监督（指挥官必须全程跟踪每个子代理的进度和状态，及时响应失败和超时）
